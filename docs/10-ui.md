## 1. Surfaces

| Surface | Audience | Tech |
|---|---|---|
| **CLI shell** (`aios`) | operators, headless | Python/rich (terminal) |
| **Web desktop** | operators, reviewers | TypeScript + React (browser) |
| **REST + WebSocket API** | programmatic control | FastAPI (kernel control plane) |

All three surfaces talk to the same **control plane** — there is one supervision model, three
rendering faces.

## 2. CLI Shell

```text
$ aios launch specs/research_analyst.json --args '{"task": "Q3 competitive landscape"}'
agent launched: pid 42

$ aios ps
PID  STATE     PRIO  GROUP  TOKENS    COST      WALL    LAST_ACTIVITY
1    RUNNING   100   shell  —         —         —       —
42   RUNNING   50    teamA  118,204   $0.42     6m12s   2s ago
43   BLOCKED   50    teamA  9,841     $0.03     1m01s   waiting: msg from 42

$ aios attach 42          # interactive chat with the running agent
$ aios suspend 42         # checkpoint + suspend
$ aios resume 42          # restore + requeue
$ aios logs 42 --follow   # stream agent console + audit events
$ aios fs-search "the Q3 analysis"
$ aios tool list          # registry view
$ aios approve t-91       # approve a pending permission ticket
$ aios top                # scheduler view (queues, budgets, utilization)
```

## 3. Web Desktop

**Implemented (Phase 4)** in [`web/`](../web/) — React + TypeScript + Vite. When
`web/dist` is built (`cd web && npm run build`), `aios serve` serves the desktop
same-origin at `http://127.0.0.1:8000/` (dev mode: `npm run dev` on port 5173
proxies `/v1` to the control plane). Sign in with an operator API key — with no
`AIOS_API_KEYS` set, the dev key `dev-key` (operator role) is enabled — or with
**single sign-on** (OIDC + PKCE, §4) when an identity provider is configured.

A browser desktop for supervising the agent fleet:

```
┌──────────────────────────────────────────────────────────────┐
│  ⚙ AI OS        [Processes] [Scheduler] [Audit] [Approvals]  │
│                    [Files] [LLM]                              │
├──────────────────────────────────────────────────────────────┤
│  ┌ Processes ──────────────────────────────────────────────┐  │
│  │ 42 research-analyst   ● RUNNING  6m   $0.42  [attach]   │  │
│  │ 43 summarizer         ◐ BLOCKED  1m   $0.03  [attach]   │  │
│  │ 44 crawler            ⏸ SUSPENDED  —   $1.12  [resume]  │  │
│  └─────────────────────────────────────────────────────────┘  │
│  ┌ Console: pid 42 (drawer) ───────────────────────────────┐  │
│  │  live log tail + operator chat (delivered via mailbox)  │  │

└──────────────────────────────────────────────────────────────┘
```

### Panels (implemented)
- **Processes** — live process table (WS feed); spawn (spec JSON), suspend/resume/kill, attach console.
- **Scheduler** — running/ready/blocked queues, utilization gauge, dispatch/preemption counters, per-agent wait stats.
- **Audit** — filtered live audit stream (REST tail + WS), hash-chain **verify** with tamper status.
- **Approvals** — pending `request_permission` tickets with one-click approve/deny (operator role).
- **Files** — semantic `fs_search` for a chosen agent (ranked hits by meaning, not path).
- **LLM** — provider failover health (`GET /v1/llm`): healthy/degraded/down, requests, failures.

### Real-time transport
- WebSocket pushes process table snapshots (~1 Hz), scheduler snapshots (~1 Hz), and audit
  entries as they land (`/v1/ws/feed`); per-agent console tails stream over
  `/v1/agents/{pid}/ws/console`. Both handshake with the JWT via `?token=`.
- REST endpoints mirror the control SDK for programmatic use.
- Security: the desktop shell + asset paths get a narrowed CSP (own scripts/styles +
  same-origin REST/WS); every `/v1` route keeps the strict `default-src 'none'` policy.

## 4. Control Plane API (REST, v1)

| Endpoint | Method | Purpose |
|---|---|---|
| `/v1/health` | GET | liveness + agent count (public) |
| `/v1/auth/token` | POST | exchange API key for a short-lived JWT (public) |
| `/v1/auth/oidc` | GET | OIDC availability + issuer (public) |
| `/v1/auth/oidc/authorize` | POST | start the PKCE flow → provider authorize URL (public) |
| `/v1/auth/oidc/callback` | GET | IdP redirect: exchange code → one-time grant cookie (public) |
| `/v1/auth/oidc/session` | POST | exchange the grant cookie for a JWT (public, cookie-only) |
| `/v1/agents` | POST | launch agent (spec) |
| `/v1/agents` | GET | process table (live ACB + tombstones) |
| `/v1/agents/{pid}` | GET / PATCH / DELETE | status / suspend,resume,kill / kill |
| `/v1/agents/{pid}/logs` | GET | console log tail |
| `/v1/agents/{pid}/messages` | POST | send a message to an agent (operator chat) |
| `/v1/agents/{pid}/ws/console` | WS | stream console lines (JWT via `?token=`) |
| `/v1/ws/feed` | WS | global feed: audit entries + scheduler/process snapshots |
| `/v1/scheduler` | GET | queues, utilization, dispatch/preempt, wait stats |
| `/v1/llm` | GET | provider failover health (`provider_status()`) |
| `/v1/approvals` | GET | list tickets (operator) |
| `/v1/approvals/{ticket_id}/approve` `/deny` | POST | decide a ticket (operator) |
| `/v1/tools` | GET | tool registry snapshot |
| `/v1/mcp/servers` | GET | registered MCP servers |
| `/v1/fs/search` | POST | semantic artifact search |
| `/v1/audit` | GET | filtered audit query (operator) |
| `/v1/audit/verify` | GET | hash-chain integrity check (operator) |

Auth: API keys for humans (`operator`/`standard` roles), JWT for the web desktop; every control
request is itself audited. Without `AIOS_API_KEYS`, the dev key is `dev-key` (operator):

```bash
curl -X POST http://127.0.0.1:8000/v1/auth/token \
  -H 'content-type: application/json' -d '{"api_key": "dev-key"}'
# → {"access_token": "<jwt>", "role": "operator", ...}
# then: Authorization: Bearer <jwt>  (or X-API-Key: dev-key)
```

### OIDC single sign-on (Slice 5.3)

Human authentication can be delegated to any standards-compliant OIDC provider
via the **authorization-code flow with PKCE** (RFC 7636). Configure at boot:

| Env var | Meaning |
|---|---|
| `AIOS_OIDC_ISSUER` | provider issuer URL, e.g. `https://accounts.google.com/` (required to enable) |
| `AIOS_OIDC_CLIENT_ID` | the desktop's public OIDC client id (required) |
| `AIOS_OIDC_CLIENT_SECRET` | optional — confidential client (PKCE stays on) |
| `AIOS_OIDC_REDIRECT_URI` | optional — defaults to `<base>/v1/auth/oidc/callback` |
| `AIOS_OIDC_SCOPES` | `"openid profile email"` by default |
| `AIOS_OIDC_ROLE_CLAIM` | claim holding group/role values (default `groups`) |
| `AIOS_OIDC_OPERATOR_VALUES` | comma-separated claim values → `operator` role |
| `AIOS_OIDC_ADMIN_EMAILS` | comma-separated emails → `operator` role |
| `AIOS_OIDC_POST_LOGIN` | relative path to land after login (default `/`) |
| `AIOS_OIDC_TIMEOUT_S` / `AIOS_OIDC_CACHE_TTL_S` | provider HTTP timeout / discovery-JWKS cache TTL |

Flow (the web desktop does this for you — a *Sign in with SSO* button appears on
the login card when OIDC is enabled):

1. `POST /v1/auth/oidc/authorize` builds the provider URL with a server-side
   PKCE `code_challenge`, `state`, and `nonce` (single-use, TTL-expiring).
2. The human completes the provider's consent screen; the provider redirects
   back to `/v1/auth/oidc/callback`. The code is exchanged (PKCE-verified), the
   ID token's signature (RS256/ES256, provider JWKS) and claims
   (issuer/audience/expiry/nonce) are verified, and the resolved principal is
   set as a short-lived **one-time HttpOnly grant cookie** (path-scoped to
   `/v1/auth/oidc`), then the browser is redirected to `AIOS_OIDC_POST_LOGIN`.
3. The desktop auto-exchanges the grant (`POST /v1/auth/oidc/session`) for the
   same JWT shape API-key login returns — one time only, so a stolen cookie
   cannot be replayed.

Role mapping is **deny-by-default**: with `AIOS_OIDC_ADMIN_EMAILS` or
`AIOS_OIDC_OPERATOR_VALUES` configured, only matching identities reach the
`operator` role (unverified emails never do); with *neither* configured every
authenticated user is `operator` and the server logs a loud warning at boot.
Coverage: `tests/unit/test_oidc.py` + `tests/integration/test_oidc_api.py`.

Dev note: with the Vite proxy (`npm run dev`, port 5173) the IdP must be told
`AIOS_OIDC_REDIRECT_URI=http://localhost:5173/v1/auth/oidc/callback` — the proxy
does not rewrite `Host`, so the auto-derived URL would point at the API port.

## 5. Human-in-the-Loop

- Operators **chat with agents** (`attach`) — messages flow through IPC (agents see them via
  `recv_msg`).
- Approval tickets surface in CLI *and* web UI; decisions are audited.
- The shell PID is the parent of operator-launched agents — the agent tree mirrors the
  organizational chain of command, and access control can express "agent may only message its
  ancestors/descendants."

## 6. Web Desktop Design Notes

- **Tech:** React + TypeScript, Vite build, WebSocket client for live panels. No heavy desktop
  framework needed — this is a *dashboard*, not an OS-in-the-browser (the kernel is the OS).
- **Security:** UI is read-mostly; state changes require explicit, audited control actions.
  No agent console content is rendered as HTML (escape by default) — agent output is untrusted.
- **Accessibility:** panels are keyboard-navigable; console supports standard terminal UX.

## 7. Open Design Decisions (to resolve at implementation)

1. **CLI vs web first** — **Resolved (Phases 1–3):** CLI first (it exercises the control API
   cheapest; shipped as `aios demo|run|resume`). The sketched control commands below
   (`ps`, `logs`, `suspend`, `approve`, …) land with the **Phase 4** REST/WS control API, and
   the web desktop follows per `11-roadmap.md` §6.
2. **Console streaming volume** — per-agent console buffers capped (e.g. last 2,000 lines) and
   paginated; full transcripts live in audit-adjacent storage when `record:true`.
3. **Attach semantics** — attach as *observer* vs. *participant* (observer is default; messages
   require explicit `/messages` action, which is audited and visible to the agent).
4. **Multi-tenant UI** — one desktop per group/tenant in v1; cross-tenant views operator-only.
