## 1. Surfaces

| Surface | Audience | Tech |
|---|---|---|
| **CLI shell** (`aios`) | operators, headless | Python/rich (terminal) |
| **Web desktop** | operators, reviewers | TypeScript + React (browser) |
| **REST + WebSocket API** | programmatic control | FastAPI (kernel control plane) |

All three surfaces talk to the same **control plane** — there is one supervision model, three
rendering faces.

## 2. CLI Shell

```text
$ aios launch specs/research_analyst.json --args '{"task": "Q3 competitive landscape"}'
agent launched: pid 42

$ aios ps
PID  STATE     PRIO  GROUP  TOKENS    COST      WALL    LAST_ACTIVITY
1    RUNNING   100   shell  —         —         —       —
42   RUNNING   50    teamA  118,204   $0.42     6m12s   2s ago
43   BLOCKED   50    teamA  9,841     $0.03     1m01s   waiting: msg from 42

$ aios attach 42          # interactive chat with the running agent
$ aios suspend 42         # checkpoint + suspend
$ aios resume 42          # restore + requeue
$ aios logs 42 --follow   # stream agent console + audit events
$ aios fs-search "the Q3 analysis"
$ aios tool list          # registry view
$ aios approve t-91       # approve a pending permission ticket
$ aios top                # scheduler view (queues, budgets, utilization)
```

## 3. Web Desktop

A browser desktop for supervising the agent fleet:

```
┌──────────────────────────────────────────────────────────────┐
│  ⚙ AI OS        [Processes] [Scheduler] [Memory] [FS] [Audit]│
├──────────────────────────────────────────────────────────────┤
│  ┌ Processes ──────────────────────────────────────────────┐  │
│  │ 42 research-analyst   ● RUNNING  6m   $0.42  [attach]   │  │
│  │ 43 summarizer         ◐ BLOCKED  1m   $0.03  [attach]   │  │
│  │ 44 crawler            ⏸ SUSPENDED  —   $1.12  [resume]  │  │
│  └─────────────────────────────────────────────────────────┘  │
│  ┌ Inspector: pid 42 ─────────────────────────────────────┐  │
│  │ [Console] [Memory] [Tools] [Budget] [Checkpoints]      │  │
│  │  ◀ agent transcript ────── ▶  token burn-down chart    │  │
│  └─────────────────────────────────────────────────────────┘  │
└──────────────────────────────────────────────────────────────┘
```

### Panels
- **Processes** — live process table, searchable; spawn/suspend/resume/kill/attach.
- **Scheduler** — queue depths per tier, preemption counts, fairness stats, budget burn-down.
- **Memory** — per-agent L1/L2/L3 usage, shared pools, retrieval preview (`search_memory`).
- **File System** — path browser **and** natural-language search (`fs_search`).
- **Audit** — filtered audit stream (syscalls, approvals, tool calls) with tamper check status.
- **Approvals** — pending `request_permission` tickets with one-click approve/deny.

### Real-time transport
- WebSocket pushes process table deltas, scheduler events, agent console lines, approval tickets.
- REST endpoints mirror the control SDK for programmatic use.

## 4. Control Plane API (REST, v1)

| Endpoint | Method | Purpose |
|---|---|---|
| `/v1/agents` | POST | launch agent (spec + args) |
| `/v1/agents/{pid}` | GET / PATCH / DELETE | status / suspend,resume / kill |
| `/v1/agents` | GET | process table (filters: state, group, owner) |
| `/v1/agents/{pid}/console` | WS | stream console + audit events |
| `/v1/agents/{pid}/messages` | POST | send a message to an agent (human-in-the-loop) |
| `/v1/approvals` | GET / POST | list / decide tickets |
| `/v1/tools` | GET | registry snapshot |
| `/v1/scheduler` | GET | queues, budgets, utilization |
| `/v1/fs/search` | POST | semantic file search |
| `/v1/audit` | GET | filtered audit query (operator-gated) |

Auth: API keys for humans (`operator`/`standard` roles), JWT for the web desktop; every control
request is itself audited.

## 5. Human-in-the-Loop

- Operators **chat with agents** (`attach`) — messages flow through IPC (agents see them via
  `recv_msg`).
- Approval tickets surface in CLI *and* web UI; decisions are audited.
- The shell PID is the parent of operator-launched agents — the agent tree mirrors the
  organizational chain of command, and access control can express "agent may only message its
  ancestors/descendants."

## 6. Web Desktop Design Notes

- **Tech:** React + TypeScript, Vite build, WebSocket client for live panels. No heavy desktop
  framework needed — this is a *dashboard*, not an OS-in-the-browser (the kernel is the OS).
- **Security:** UI is read-mostly; state changes require explicit, audited control actions.
  No agent console content is rendered as HTML (escape by default) — agent output is untrusted.
- **Accessibility:** panels are keyboard-navigable; console supports standard terminal UX.

## 7. Open Design Decisions (to resolve at implementation)

1. **CLI vs web first** — recommend CLI first (it exercises the control API cheapest); web
   desktop in Phase 3 once the API surface is stable.
2. **Console streaming volume** — per-agent console buffers capped (e.g. last 2,000 lines) and
   paginated; full transcripts live in audit-adjacent storage when `record:true`.
3. **Attach semantics** — attach as *observer* vs. *participant* (observer is default; messages
   require explicit `/messages` action, which is audited and visible to the agent).
4. **Multi-tenant UI** — one desktop per group/tenant in v1; cross-tenant views operator-only.
